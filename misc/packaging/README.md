# RPM and Debian packages

`goreleaser` builds these packages per architecture (`nfpms` in
`.goreleaser.yaml`), attached to each GitHub release:

- `xolo`: the server, `xolo-migrate`, `xolo-adoption`, `xolo-admin` (which runs
  the last two with the environment and the account of the service), the systemd unit, its
  environment file and the declaration of the `xolo` system account;
- `xolo-plugin-<name>`: one official plugin under `/usr/lib/xolo/plugins`,
  depending on `xolo`;
- `xolo-plugin-all`: a metapackage depending on every plugin package. `xolo`
  only suggests it: apt and dnf install recommendations by default, which would
  bring every plugin with the server.

A plugin added to `builds` needs its own `nfpms` entry and a line in the
dependencies of `xolo-plugin-all`, as it needs a line in the Docker image.

## What the packages rely on

- Binaries are built with `CGO_ENABLED=0`: they are static and do not depend on
  the C library of the build machine, which is what lets one package serve
  every release of a distribution.
- The account is created by the pre-installation script, through
  `systemd-sysusers` when there is one and `useradd` otherwise, because
  `/etc/xolo/xolo.env` belongs to the `xolo` group and is unpacked before any
  `sysusers.d` file is read.
- `/etc/xolo/secret.env` is generated by the post-installation script and is
  not a file of the package: no upgrade, removal or purge touches it.
- The service is never enabled nor started by the package. An upgrade restarts
  it when it was running.
- The server lists its plugins at startup only, so a plugin package installed,
  upgraded or removed restarts it, once per command whatever the number of
  plugins: on Debian, `xolo` declares a dpkg trigger on
  `/usr/lib/xolo/plugins` and its post-installation script runs once at the
  end; on RPM, each plugin leaves a marker under `/run/xolo-packages` and the
  first post-transaction script to find it restarts. rpm runs no
  post-transaction script for an erased package, and a restart per removed
  package trips the start limit of systemd (5 starts in 10 s): the first
  removal schedules one restart 5 s later with `systemd-run`, under a unit name
  the next removals find taken.

## Testing

```bash
make packages        # dist/*.rpm, dist/*.deb
make test-packages   # installs them on RHEL 10, RHEL 9, Debian 13 and Debian 12
```

`test.sh` boots each distribution in a privileged container with systemd as
PID 1, the Red Hat ones from the Universal Base Images, and runs
`test/check.sh` there: installation, account and permissions, start of the
service under the hardening of the unit, plugins loaded, reinstallation,
removal. `XOLO_PACKAGE_TARGETS=rhel10 make test-packages` restricts the run.
The `build` job of the `check` workflow runs it on every pull request.

What it does not cover: SELinux in enforcing mode, which a container cannot
exercise, and the `arm64` packages, built but installed nowhere.
